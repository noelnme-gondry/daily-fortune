# 배포 간 정적 자산 보존

기존 HTML 또는 JS가 다음 배포 이후에도 원래 해시 URL의 바이트를 받을 수 있도록 빌드 산출물을 소스와 함께 전달한다. 검색 색인 회복을 보장하는 기능은 아니다.

## 전달 계약

- `release-assets/catalog.json`: 준비된 릴리즈 ID, 소스 기준 SHA, 준비/마지막 참조 시각, 확인된 운영 릴리즈, 종료 시각, 원본 Vite manifest, 파일별 SHA-256·크기·MIME·참조 관계.
- `release-assets/blobs/<sha256>.gz`: 변경할 수 없는 원본 자산. 서로 다른 릴리즈가 같은 파일을 사용하면 한 번만 저장한다. gzip을 풀어 SHA-256을 확인한 뒤 원래 `assets/...` 경로에 복원한다.
- Vite manifest의 static/dynamic import 그래프를 그대로 기록하며, 출력 문자열의 파일명 참조도 보조 관계로 기록한다. 보조 관계는 보수적인 목록이며 JS 구문 분석 결과는 아니다. **보관 단위는 manifest에서 도달 가능한 일부 파일이 아니라 `dist/assets`의 전체 파일**이다. manifest에 없는 Worker와 CSS의 폰트·이미지도 빠지지 않는다.
- `/data/`, `/characters/` 등 기존 public의 비해시 URL은 현재의 별도 계약을 유지한다. 이 작업은 이 파일의 과거 버전을 제공하거나 API 호환성을 보장하지 않는다.
- HTML은 현재 manifest만 읽는다. 과거 manifest로 HTML을 생성하지 않으며, 오래된 URL을 새 JS로 바꾸거나 리디렉션하지 않는다. 알 수 없는 자산은 기존 Express static의 404를 유지한다.

보존 묶음은 Git에 포함해 Railway의 깨끗한 체크아웃에도 들어가도록 설계했다. 새 서비스·볼륨·자격 증명은 필요 없다. Git 이력에는 과거 blob이 계속 남으므로 저장소 전체 용량은 작업 트리의 보존량보다 커질 수 있다. 이번 구현 작업에서는 커밋·push·배포를 하지 않는다.

## 릴리즈 준비와 검증

1. 자산 관련 코드를 수정한 뒤 배포와 같은 Node·lockfile·`VITE_` 환경에서 `npm run release:prepare`를 실행한다. Vite의 `emptyOutDir: true`로 새 빌드를 만든 후 manifest와 자산 전체를 보존 묶음에 기록한다. 기존 dist를 입력으로 자동 누적하지 않는다.
2. 소스 변경, `release-assets/catalog.json`, 추가 blob을 검토한다. 일반 `npm run build`는 새 빌드 뒤 이전 자산을 복원한다. `npm run build:release`는 준비된 현재 릴리즈와 빌드 출력의 파일·바이트·manifest가 일치해야 복원한다. 일치하지 않으면 배포 빌드를 실패시켜 준비 누락을 드러낸다.
3. `npm run test:all`, `npm run lint`, `npm run build`와 필요 시 `npm run build:release`를 실행한다. 검증 후 사용자 승인 범위에서 변경 파일만 명시적으로 stage·commit한다. 생성되는 catalog/blob도 함께 전달해야 한다.
4. Railway 설정 파일과 CI는 `npm run build:release`를 사용한다. Railway 대시보드에 별도의 빌드 명령 덮어쓰기가 있다면 실제 배포 전에 파일 설정이 적용되는지 확인해야 한다. 이번에는 계정 설정을 변경하지 않았다.

`build:current`는 내부 구성 명령이며 보존 복원을 하지 않는다. 배포 명령으로 사용하지 않는다. 자산 검사는 깨끗한 Vite 출력에 적용하므로 `release-assets.mjs verify`를 복원 후 dist에 따로 반복 실행하지 않고 `npm run build:release`를 사용한다. 빌드가 만드는 내용을 변경하는 환경 변수가 다르면 같은 소스 SHA여도 준비를 다시 해야 한다.

현재 묶음은 `ebfe1e084eeda631e4bcfc2860d55ef4534623b0`을 기준으로 2026-11-13에 새로 빌드해 준비했다. `sourceRevision`은 기준 커밋이며 준비 중인 미커밋 변경을 식별하는 값은 아니다. 실제 산출물 식별자는 manifest와 파일별 메타데이터의 SHA-256인 릴리즈 ID다. 이 묶음은 과거 운영 산출물을 내려받아 검증한 자료가 아니다.

## 보존과 정리

`scripts/lib/release-assets.mjs`의 `RETENTION_DAYS`가 유일한 보존 기간 설정이며 초기값은 30일이다. 기간을 늘리려면 이 값을 변경하고 경계 테스트를 실행한다. 최근 두 배포만 남기는 규칙을 사용하지 않는다.

준비 시각과 실제 배포 시각은 다르다. **운영 배포 성공을 확인한 후에만** 다음 로컬 기록 명령에 성공한 릴리즈 ID와 완료 시각을 입력한다.

```sh
node scripts/release-assets.mjs record-deployment <release-id> <ISO-8601-time>
```

이 명령은 외부 배포를 실행하지 않는다. 새 운영 릴리즈의 마지막 참조 시각을 갱신하고, 이전 운영 릴리즈의 마지막 참조·종료 시각을 같은 시각으로 기록한다. 수개월 동안 유지된 릴리즈가 다음 배포 즉시 만료되지 않도록 **운영 종료 후에도 최소 30일**을 더 보존한다. 기록 변경은 다음 소스 전달에 포함한다. 누락 시 삭제가 늦어지므로 보존 쪽으로 동작한다.

```sh
npm run release:prune             # 삭제 후보만 출력
npm run release:prune -- --apply  # 검토한 후보를 로컬 보존 묶음에서 정리
```

- 빌드·준비·서버 시작에서는 자동 삭제하지 않는다.
- 현재 준비 릴리즈, 운영 중 릴리즈, 배포 종료가 확인되지 않은 릴리즈는 삭제하지 않는다.
- 종료 시각부터 정확히 30일인 경계도 보존하며, 이를 초과한 종료 릴리즈만 정리 후보가 된다.
- 남겨진 릴리즈가 참조하는 공유 파일과 같은 checksum blob은 삭제하지 않는다. 파일 목록은 catalog에서 파생한다.
- 정리는 보존 묶음만 바꾼다. 이미 복원된 dist는 건드리지 않고, 다음 깨끗한 빌드에 적용된다. 실제 요청이 계속되면 적용 전에 기간을 늘린다.

## 용량과 과거 파일의 한계

최초 묶음은 21개 자산, 원본 1,751,850바이트이며 catalog와 gzip blob 합계는 약 598KB다. 변경 없는 파일은 중복 저장하지 않는다. 매일 모든 파일이 바뀐다고 가정한 30개 묶음은 압축 파일 기준 약 17.4MiB 규모의 단순 추정이며, 미래 자산 증가·미확인 배포 묶음·Git 이력 용량은 포함하지 않는다. 배포 종료 기록이 없으면 보존 기간과 관계없이 계속 남는다.

문제 보고의 `style-D3-S-Esk.css`, `main-CXudPc8H.js`는 검증 가능한 원본을 확보하지 못했다. 최신 파일을 이 이름으로 복사하지 않았으며 두 URL의 과거 복구를 완료한 것으로 보고하지 않는다. 초기 묶음의 현재 파일명이 운영 관측과 일치하더라도 과거 운영 원본의 checksum을 입증하는 것은 아니다.

## 회귀 검증 범위

단위 검사는 동일 URL의 바이트 충돌, 손상 blob, 경로 탈출·심볼릭 링크, 보존 경계와 공유 의존 파일을 검사한다. 브라우저 검사는 A의 HTML을 보관하고 B를 빈 작업 공간에서 빌드해 기존 URL 404를 먼저 재현한다. 보존 묶음을 전달한 뒤 실제 Railway 빌드 명령으로 B를 재생성하고 A 전체 자산의 GET/HEAD·MIME·SHA-256·nosniff·immutable을 확인한다.

A HTML을 B 서버에 연결해 이전 진입 스크립트와 동적 import로 실제 계산을 수행하고, B의 오늘·내일·영어 오늘·만세력 진입과 KST 자정 전후 공개 예시를 확인한다. Googlebot UA 비교는 로컬 응답 일관성 검사이며 실제 Googlebot 수집 증거가 아니다. 운영 배포 후 검증과 `/today/`의 검색 색인 상태는 별도다.
